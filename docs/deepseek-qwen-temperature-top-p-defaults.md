# DeepSeek / Qwen 的 `temperature`、`top_p` 官方默认值核查

## Answer

本地保存的阿里云与火山方舟官方文档给出的答案并不对称：

| 接口/模型范围 | `temperature` | `top_p` | 证据性质 |
|---|---:|---:|---|
| 火山方舟 Responses API | 默认 **1.0** | 默认 **0.7** | 接口级默认值；文档没有明确标注为 DeepSeek 专属默认值 |
| 阿里云百炼 Responses API（含 qwen3.7 / qwen3.8 等） | **未公布数值默认值** | **未公布数值默认值** | 参数表只写可选、范围和调节建议 |
| 阿里云文本生成“翻译”场景 | **0.3** | **0.8** | 推荐配置示例，不是 Qwen 模型默认值 |

因此，针对本项目的 `deepseek-v4-flash/pro` 与 `qwen3.7-plus/max、qwen3.8-max`，能够严格成立的结论是：

- 方舟文档明确给出了 Responses **接口默认** `temperature=1.0、top_p=0.7`，但没有在本地文档中逐型号确认 DeepSeek V4 是否继承该值；将其用于 DeepSeek V4 是基于接口规则及未列入例外名单所作的推断，不应写成“DeepSeek 模型官方默认”。
- 阿里云文档没有为上述 Qwen 型号公布 `temperature` 或 `top_p` 的服务端默认数值。`0.3 / 0.8` 是翻译场景推荐配置，不是默认配置。

### API 响应是否回显默认值

| 平台 | 省略请求参数后的文档行为 | 能否从响应取得有效默认值 |
|---|---|---|
| 火山方舟 | 响应结构将 `temperature`、`top_p` 定义为“本次请求实际使用”的数值 | **按文档契约可以**；结合请求默认，应分别回显 `1.0`、`0.7`，但本地资料没有省略参数后的完整响应实例 |
| 阿里云百炼 | Qwen 示例从 `response.created` 到 `response.completed` 均返回 `temperature:null`、`top_p:null` | **不可以**；字段存在，但没有回显解析后的有效默认数值 |

## Evidence

### 火山方舟

《创建 Response》PDF 的请求参数表明确写明 `temperature` 默认值为 **1.0**、取值范围为 `[0, 2]`。同一条目列出的固定值例外只有三个 Doubao Seed 2.0 型号，没有出现 DeepSeek。证据位于 [`火山方舟_创建Response_1784703795.pdf`](./火山方舟_创建Response_1784703795.pdf) 的 PDF 第 31 页（文档页脚 28/68）。

同一 PDF 明确写明 `top_p` 默认值为 **0.7**、取值范围为 `[0, 1]`，并建议通常只调整 `temperature` 或 `top_p` 之一。固定为 `0.95` 的例外列表同样只包含若干 Doubao Seed 型号，没有出现 DeepSeek。证据位于该 PDF 第 41 页（文档页脚 38/68）。

该 PDF 的“响应参数”章节又把 `temperature` 定义为“本次请求实际使用的采样温度”，把 `top_p` 定义为“本次请求实际使用的核采样概率阈值”。这说明方舟响应对象的设计目标是回显有效值，而不只是回显调用方是否传参。证据分别位于 PDF 第 60 页（文档页脚 57/68）和第 69 页（文档页脚 66/68）。

这些值出现在通用 Responses 请求参数定义中，而不是 DeepSeek 型号说明中。PDF 全文没有 `DeepSeek` 字样，且把具体模型能力/上限导向外部“模型列表”。因此，它能证明方舟 Responses 接口文档声明的默认值，却不能单独证明某个 DeepSeek V4 推理接入点没有额外覆盖。

另一份方舟官方资料《语言模型》只给出范围和效果：`Temperature` 为 `0–2.0`，`TopP` 为 `0–1.0`，没有给出默认数值。[`火山方舟-语言模型.md` 第 29–35 行](./火山方舟-语言模型.md#L29-L35)

### 阿里云百炼 / Qwen

阿里云 Responses API 参数表将 `temperature` 和 `top_p` 标为可选参数，分别给出 `[0, 2)` 与 `(0, 1.0]` 的范围，并建议只设置其中一个；两条参数说明均没有“默认值”字段。[`阿里云-OpenAI兼容-Responses创建响应.md` 第 85–86 行](./阿里云-OpenAI兼容-Responses创建响应.md#L85-L86)

该 Responses 文档明确覆盖 `qwen3.8-max`、`qwen3.7-max`、`qwen3.7-plus` 等型号，所以“未公布默认数值”正是这些 Qwen Responses 调用的文档状态，而不是因为它们不在接口范围内。[`阿里云-OpenAI兼容-Responses创建响应.md` 第 76 行](./阿里云-OpenAI兼容-Responses创建响应.md#L76)

Responses 流式示例在省略这两个请求参数后，响应对象显示 `temperature:null`、`top_p:null`。这只能证明响应没有回显一个数值，不能把 `null` 解释为模型内部采样温度或核采样阈值。[`阿里云-OpenAI兼容-Responses.md` 第 567–585 行](./阿里云-OpenAI兼容-Responses.md#L567-L585)

其中最终 `response.completed` 对象的模型已经明确为 `qwen3.7-plus`，两字段仍为 `null`；因此这不是仅发生在排队或生成中的临时状态。阿里云示例证明响应包含这两个字段，但不返回服务端实际采用的数值默认值。

《文本生成-概述》把翻译列入“不同场景的推荐参数配置”，对应 `temperature=0.3、top_p=0.8`。由于该段标题和代码注释分别是“参数配置示例”与“推荐参数配置”，这两个数字是建议值，不是 Qwen 的默认值。[`阿里云-文本生成-概述.md` 第 1525–1550 行](./阿里云-文本生成-概述.md#L1525-L1550)

同一资料只说明参数范围、作用和建议一次调整一个参数，也没有在这里声明 Qwen 的默认值。[`阿里云-文本生成-概述.md` 第 1479–1488 行](./阿里云-文本生成-概述.md#L1479-L1488)

## Limitations and unknowns

本次范围限定为 `docs/` 中以“阿里云”或“火山方舟”命名的七份本地官方资料。`baseinfo.md`、`quality_control.md` 等项目内部汇总虽然也记录了采样参数，但不是厂商原始文档，因此没有用来证明官方默认值。

方舟 PDF 的通用参数默认值没有逐一绑定到 DeepSeek V4 型号；要把 `1.0 / 0.7` 升级为该型号的确定契约，还需要对应推理接入点的当前模型卡、在线 API 文档，或一次“不传参数”且服务端能回显有效采样配置的验证。当前本地文档不足以排除网关或模型层覆盖。

方舟本地文档没有给出一条省略 `temperature`、`top_p` 后的完整 JSON 响应，所以“会回显 `1.0 / 0.7`”是由请求默认值与响应字段“实际使用值”两项契约组合得出的结论，尚未由本地运行样本验证。

阿里云在响应中返回 `null` 也没有暴露内部实际采用的采样值。因此，仅凭不传参数后的正常生成结果，无法反推出 Qwen 默认值。

## Decision impact

如果目标是复现或公平比较 DeepSeek 与 Qwen，不应把“省略参数”视为两家使用了相同默认值：方舟文档写的是 `1.0 / 0.7`，而阿里云没有公开 Qwen Responses 的数值默认值。

若需要可复现实验，应显式记录并传入选定参数；若目标是观察各厂商默认行为，则应同时省略两个参数，并把实验标签写成“provider default / 未知有效值”，不能把阿里云侧记作 `1.0 / 1.0` 或 `0.3 / 0.8`。对于字幕翻译，阿里云官方的 `0.3 / 0.8` 可作为单独推荐配置实验，但必须与默认行为实验分开。

记录运行元数据时，方舟可以优先读取响应中的 `temperature`、`top_p` 作为实际生效值；阿里云不能依赖响应字段恢复默认采样配置，应同时记录调用方是否显式传参及传入值。即使阿里云将来在显式传参时回显数值，也不能据此假设省略参数时会回显默认值。

# Deep-grill 评审：Opus 4.6-Low 字幕翻译对齐路线图

> **状态：已失效（2026-08-09）。** 本文评审的是“六模型 + 尚待从四份源 SRT 重新抽样”的旧路线图。用户随后提供 TQA v1 与两份已制作的翻译测试样例，仓库领域文档也已把目标固定为两个模型，并采用“隔离筛选 + 全流程确认”。因此，本文的总体结论、spec-readiness gates、ticket 修订要求和建议顺序均不得作为当前路线的审核依据；其中代码事实也未在本次修订中重新验证。文件仅保留为历史记录。新的有效评审须以修订后的 [`map.md`](map.md)、TQA v1、两份样例及当时代码为输入重新执行。

## 结论

**路线方向可行，但当前状态不足以直接生成可执行 spec。**

- 对“继续把它作为研究路线图推进”的裁决：**支持，但须修订**。
- 对“现在就交给 `to-spec` 生成实施规格”的裁决：**拒绝**。
- 对最终目标“产出一份可执行、可验收的 spec 文档”的裁决：**可以达到**，前提是先关闭本文列出的 spec-readiness gates。

这不是一条死路。路线图已经正确识别了参考译文、连续语境样本、provider 差异、一次只调一个采样参数、盲评和 holdout 等关键问题。阻止它现在进入 spec 的，不是缺少更多想法，而是几项会改变实验含义的决策和代码事实仍停留在 fog 或 open ticket 中。

## 最高风险异议

### C1. 小样本运行并没有保留“整集通读”语境

**证据状态：充分。**

当前流程先解析整份 SRT，再通过 `cue_offset/max_cues` 切片；摘要生成器接收的是切片后的 `cues`，不是 `all_cues`。同一组 `temperature/top_p` 又同时传给摘要调用和后续翻译调用（[`pipeline/orchestrator.py`](../../pipeline/orchestrator.py)，L70-L112）。

**最强异议：**路线图把“连续上下文小样本”与“保持现有通读摘要流程”并列，但现有 CLI 只能做到“通读所选切片”，不能做到“通读整集、只翻译诊断窗口”。

**具体失败场景：**某个需要前半集人物关系才能消歧的窗口，被单独切片后生成了局部摘要。候选 A 因为局部摘要碰巧猜对而胜出；全量运行时整集摘要改变，排名反转。最终 spec 声称参数使输出接近 Low，实际只证明参数适合一个被截断语境。

**裁决：修订，不接受现状。** Ticket 03 必须显式决定以下两种实验主张中的一种：

1. **端到端小样本筛选：**承认摘要也随 sampling 改变、摘要只覆盖窗口；结论仅用于淘汰明显失败项，不作翻译阶段因果归因。
2. **隔离式参数筛选：**固定由完整剧集生成且带哈希的摘要，只改变翻译请求 sampling；这需要一个非生产实验外壳或最小注入点，因为现有 CLI 不支持复用既有摘要。

如果选择第 2 种，确实需要修改或新增代码。原因不是改变产品流程，而是当前接口没有“完整剧集摘要 + 仅翻译选定窗口 + 固定摘要复用”的表达能力。该工具必须位于实验边界，不能改变生产默认行为。最终 finalist 仍须用原始端到端流程复验，防止隔离筛选结果无法迁移。

**负责人 / 触发点：**Ticket 03 research 提出证据化方案；用户批准是否接受非生产实验工具；任何模型调用前关闭。

### C2. “达到 Opus 4.6-Low”目前不可判定

**证据状态：不足。**

Ticket 01 正确指出：字符串接近不能证明自然度，主观偏好也不能自动变成阈值（[`tickets/01-define-opus-low-parity.md`](tickets/01-define-opus-low-parity.md)，L9-L27）。Ticket 06 仍未定义尺度、阈值、盲评和分歧处理（[`tickets/06-define-evaluation-rubric.md`](tickets/06-define-evaluation-rubric.md)，L9-L28）。

**最强异议：**没有先验 acceptance rule，任何赢家都可能是看完输出后再选择有利指标的结果。

**具体失败场景：**候选 A 更像 Low 的措辞但漏译，候选 B 语义完整且更自然。评审在看到结果后临时把“参考相似度”权重调高，A 被宣布达到 Low；结构正确性和语义忠实反而被风格分数补偿。

**裁决：修订。** spec 前必须冻结：

- 硬门禁：ID、条数、`src`、JSON/SRT、漏译/增译、关键语义错误；硬门禁失败不能由文风抵消；
- 质量维度：语义、语境消歧、中文口语自然度、translationese、字幕可读性、称谓/术语一致性；
- Low 的角色：参考锚点而非逐字答案；
- 盲化、随机顺序、并列与分歧处理；
- “进入下一轮”与“达到 Low”的两个不同阈值；
- 谁拥有最终裁决以及最少需要多少独立判断。

**负责人 / 触发点：**用户在 Ticket 01 拥有质量和风险取舍；Ticket 06 把决定落成可重复协议；任何评分前关闭。

## 对路线图结构的修订要求

当前 6 个 tickets 是必要的，但不足以形成完整的 spec handoff。路线图在 `map.md` L37 把 prototype、prompt A/B 和 holdout 复跑留待以后升格，这符合低分辨率规划方法；然而，“何时足以生成 spec”本身没有可观察的出口。

### 必须在现有 tickets 中补强

1. **Ticket 01：**除 Low 质量阈值外，明确全部六模型还是子集、per-model 还是统一参数、最终人工裁决者。
2. **Ticket 02：**除 Markdown 样本外，增加不可变 manifest：文件哈希、cue 范围、dev/holdout、上下文依赖、provenance 限制。
3. **Ticket 03：**显式关闭 C1 的摘要/切片边界；记录 sampling 的 wire intent；判定是否需要隔离实验工具。
4. **Ticket 05：**把 OMIT 定义为观察臂而非已知数值；冻结重复、淘汰、成本上限和只调一个参数的主矩阵。
5. **Ticket 06：**分离硬门禁与质量分；冻结盲评、阈值、分歧与“筛选通过 / Low 对齐通过”两级判定。

### 必须从 fog 升格的后续 tickets

当 Ticket 05 与 Ticket 06 都完成后，至少要升格并关闭：

1. **成本探针 / harness proof：**证明单次窗口、摘要、重试和落盘证据符合契约。
2. **逐模型 coarse-to-fine prototype：**按 provider-aware 矩阵运行并淘汰。
3. **prompt finalist A/B：**只对 sampling finalist 比较原短语与指定替换。
4. **冻结 holdout 复跑：**验证 winner 没有只拟合开发样本。
5. **全量批准决定：**用户根据质量、稳定性和成本决定是否进行昂贵的整集验证。
6. **spec handoff：**把最终决策、未决风险、运行命令与验收契约装配成单一决策包。

这些不是现在就要创建或执行的文件；它们是路线图要兑现“可以生成 spec”必须具备的可观察收敛路径。

## 最低 spec-readiness gate

只有以下项目全部为真，路线图才可以交给 `to-spec`：

- [ ] 目标模型集合与 per-model / uniform 配置形态已经由用户决定。
- [ ] “筛选通过”与“达到 Low”的阈值、硬门禁和最终裁决人已冻结。
- [ ] 四份参考 SRT 的哈希、对齐、来源声明和限制已记录。
- [ ] 诊断窗口、类别、dev/holdout 划分在看候选结果前冻结。
- [ ] 摘要/切片/sampling 的实验含义已选择：端到端效应或固定摘要隔离效应。
- [ ] 每次运行能从产物证明实际 sent/omitted 参数意图和全部固定控制变量。
- [ ] Ark 与 Aliyun 的 OMIT 不被伪装成共同默认数值。
- [ ] provider-aware matrix、复跑、晋级、早停和 token 预算已确定。
- [ ] 提示词替换只作为 finalist A/B，并受语义硬门禁约束。
- [ ] prototype 与 holdout 已给出支持或反对 finalist 的可审计证据。
- [ ] 只有通过以上门槛的 finalist 才获准进入全量验证。
- [ ] spec 明确列出剩余未知项，不把未验证推断写成模型默认或质量事实。

## 建议的决策顺序

1. 先关闭 Ticket 01 的用户决策；否则评分与最终配置形态都没有稳定目标。
2. Ticket 02 与 Ticket 03 可独立推进：前者冻结测量材料，后者冻结实验语义。
3. Ticket 04 在 Ticket 03 后审计历史证据；Ticket 06 在 Ticket 01 + 02 后冻结评分。
4. Ticket 05 在 Ticket 03 + 04 后形成最小矩阵，并吸收重复与成本规则。
5. 只有矩阵和评分都清除后，才运行 prototype、prompt A/B 和 holdout。
6. 最后形成 spec handoff，不从 open/fog 状态直接生成规格。

## 最终建议

**继续这条路线，但将当前状态标记为 `not ready for spec`。**

最先要修的不是参数点位，而是 C1：明确诊断样本究竟评估“局部摘要驱动的端到端流程”，还是“固定整集语境下翻译 sampling 的独立效果”。这个选择会改变样本载体、是否需要实验工具、成本模型、可作出的因果主张以及最终验证方式。

在该边界、Low 验收定义、运行证据链和重复/预算规则关闭后，这份路线图可以可靠地产生 spec 文档；在它们关闭前生成 spec，只会把未决定事项伪装成实施细节。
